# CloudStorage connections

Source candidate 0.8.0-dev.24 embeds runtime 0.8.0-dev.13, exposes twelve MCP tools and provides one common `cloudstorage_execute` route with explicit provider and connection ID. Its local MCP identity is `cloudstorage-portal-local`, distinct from the independent `onedrive` App declaration, so both routes remain visible. The installed dev.20/dev.11 runtime passed fresh Codex discovery, status and own-app Google root execution on 25 October 2026; the local OneDrive root adapter also returned bounded local metadata while correctly reporting that cloud identity and sync state were not verified. Earlier own-app Dropbox and OneDrive identity/root/folder/text evidence remains historical evidence for the broker, not proof that those grants are currently restored. The native App layer separately references Dropbox, Google Drive and OneDrive. This evidence does not prove cloud writes, current broker-owned Dropbox or OneDrive Graph grants, multiple distinct accounts for one provider or that an already-running chat has refreshed its MCP transport.

Use `cloudstorage_select_account` with an explicit `connection_id` to select an existing local connection. Keep all subsequent reads explicitly bound to their `connection_id`. Selection does not switch native connector accounts, grant permissions, or prove that multiple distinct accounts have passed live login. Disconnect removes only the requested local connection and its locally protected refresh grant; when that connection was selected, the broker selects another healthy connected account of the same provider when available, never an account from another provider. Runtime 0.8.0-dev.13 protects refresh grants and the Google Desktop client secret with Windows CurrentUser DPAPI under `LOCALAPPDATA/CloudStoragePortal`; the Google secret is decrypted only when token exchange or refresh needs it, access tokens remain memory-only, and a fresh OAuth state is single-use for 30 minutes. Restored grants must refresh and reproduce the same immutable provider identity before use. Consult `runtime/README.md` for registration and installation boundaries.

The runtime uses the official MCP Server SDK 2.3.1 and strict Zod schemas. Before using the local MCP runtime on a new checkout, follow `runtime/README.md` and install the locked dependencies with `npm ci --ignore-scripts`. The local hybrid plugin's accepted `mcp.json` performs host registration; merely packaging runtime files inside the private App-backed account plugin does not. Native cloud skills and provider grants remain separate from local runtime tools.

Version 0.3.0 includes a local prototype in [runtime/README.md](../../runtime/README.md), with loopback OAuth adapters and five stdio MCP tools. These tools exist in the host only after actual local configuration. For existing OneDrive sync access, use optional ONEDRIVE_LOCAL_ROOT mode without a new OAuth registration; label it local filesystem metadata access, separately from verified cloud identity and Graph authorization. Never inspect or copy OneAuth token caches to implement login.

Present one portal connection list with three required providers: Dropbox, Google Drive and OneDrive. Reuse the existing authorized native connectors for supported operations. Read [the broker contract](../cloudstorage-portal/references/oauth-broker.md) before designing a separate OAuth service.

1. Discover current tools and supported account selectors. Record provider, connection reference, observed immutable account ID, tenant if applicable, granted capabilities when observable, and verification evidence. Unknown values remain unknown.
2. Report registration, adapter availability, consent, identity verification, read verification and write verification separately for each provider. Three-provider completion requires all three identities and intended operations to be verified.
3. A unified portal session may own multiple provider connections. Each provider uses its own OAuth app registration, authorization grant and access/refresh tokens. Never reuse a Google token for Microsoft or Dropbox. Do not extract credentials from existing connectors or browser storage.
4. If implementing an independent broker, obtain the hosting/callback address and app registration status. Request no secrets in chat. Configure secrets through the deployment platform's secret manager. App registration, callback registration and interactive provider consent must actually finish before live authorization can be claimed.
5. Derive requested scopes from intended operations using current official provider documentation. Do not grant broad write scopes just because a skill exists. Treat Google file access, Docs, Sheets, Slides, Dropbox file requests and sharing, and Microsoft delegated drive access separately.
6. Bind each operation to the authenticated portal owner and exact connection. Reject cross-user IDs, revoked connections, missing scopes and account mismatch. Never silently fall back to another account.
7. Refresh server-side through the matching provider, preserve an existing refresh token if the response omits one, atomically store rotations, and reauthenticate on invalid grants. Disconnect must remove portal access and use supported provider revocation without claiming remote revocation when unverified.
8. Return a capability matrix and the exact missing setup. A saved skill or design is not a deployed OAuth server.
